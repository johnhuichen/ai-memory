> Memory: While implementing a feature, improve the code it touches only where you are sure the change is better, and clean up only what your own change made unused.

While implementing a feature, improve the code the feature touches only where you are sure the change is better, such as a clearer name or duplicate logic in a function you are already changing. Leave anything you aren't sure of, and any restructuring (moving modules, changing interfaces, adding abstractions), for the user to decide, and mention it after the task. Remove imports, variables and functions that your own change made unused, but mention older dead code instead of deleting it. A small improvement you are sure of costs little to review and leaves the codebase better. One you aren't sure of, or a restructure, is a design decision that belongs to the user, as is older dead code.

Example: while adding time-zone support to `parse_date()`, rename its variable `d` to `parsed_date` and merge the two copies of the offset calculation inside it. Don't move date parsing into a new module. If your change replaces the only call to `format_legacy()`, delete `format_legacy()` and its import. If nothing calls `parse_time()`, say so instead of deleting it.
